## Summary

RHOAI must provide a default vector store that is available out-of-the-box — without manual setup — so that Gen AI Studio and Auto Rag continue to function when inline providers are removed from the Llama Stack distribution image. Today these capabilities depend on an inline vector store provider bundled within the Llama Stack process; removing it (per RHAISTRAT-7474) will break them unless an alternative is available at the platform level.

## Problem Statement

Gen AI Studio and Auto Rag currently rely on an inline Milvus provider embedded in the Llama Stack distribution image to store and retrieve vector embeddings. This inline provider runs inside the Llama Stack process itself.

RHAISTRAT-7474 proposes removing inline providers from the Llama Stack distribution to improve GA readiness — shipping only what can be tested and maintained at scale, and aligning with Llama Stack's primary use case as a remote API server. However, no platform-level alternative exists today. If inline providers are removed without a replacement, any RHOAI user relying on Gen AI Studio's RAG capabilities or Auto Rag will lose functionality entirely — there is no workaround short of manually provisioning and configuring an external vector database.

Users expect vector storage to "just work" when they use Gen AI Studio or Auto Rag. The current out-of-the-box experience must be preserved even as the underlying architecture evolves.

## Affected Customers

* All RHOAI customers using Gen AI Studio playground with RAG capabilities
* All RHOAI customers using Auto Rag
* This is a platform-level product dependency: these features cannot function without a vector store

## Business Justification

* **Product integrity:** Gen AI Studio and Auto Rag are GA-track capabilities in RHOAI. Removing the inline vector store without a replacement breaks shipped product functionality for every user of these features.
* **Blocking dependency:** RHAISTRAT-7474 (removing inline providers for GA readiness) cannot proceed until this RFE is resolved. Silas Brenmark (Gen AI Studio lead) has identified this as a blocker.
* **User experience:** RHOAI differentiates on integrated, opinionated defaults. Requiring users to manually provision and configure a vector database before they can use the playground or Auto Rag degrades the out-of-the-box experience that customers expect from the platform.

## Acceptance Criteria

* \[ \] A default vector store is available out-of-the-box on RHOAI without requiring users to manually provision or configure external infrastructure
* \[ \] Gen AI Studio playground RAG workflows function with the default vector store with no loss of current capability
* \[ \] Auto Rag functions with the default vector store with no loss of current capability
* \[ \] The default vector store runs as a separate process, decoupled from the Llama Stack instance (not an inline provider)
* \[ \] The default vector store is scoped appropriately for multi-tenant environments (e.g., per-namespace isolation)
* \[ \] The default vector store is lightweight enough to run in resource-constrained environments without imposing significant overhead

## Success Criteria

* Users of Gen AI Studio and Auto Rag experience no functional regression when inline providers are removed from the Llama Stack distribution
* No additional manual setup steps are required for RAG workflows compared to the current experience
* RHAISTRAT-7474 is unblocked and can proceed to implementation

## Open Questions

* What is the preferred scoping model — per namespace, per Llama Stack instance, or both? (Silas noted per-namespace is preferred for isolation, but Auto Rag may need per-instance scoping)
* Should users have a migration path from the default vector store to a production-grade vector database? (Bram Sundqvist raised the importance of aligning with commonly-used vector DB providers for easier migration)

## Staff Engineer Input

**Correction 1 — OGX does not auto-provision PostgreSQL.** OGX defaults to SQLite for storage (`storage.kv.type: sqlite`, `storage.sql.type: sqlite` in the OGXServer CRD). The odh-dashboard gen-ai BFF hardcodes SQLite when creating OGXServer instances for the playground (`kv_sqlite` and `sql_sqlite` in `llamastack_config.go`). PostgreSQL is a supported backend but must be user-configured with an explicit `connectionString` secret. The strategy's claim that "every LlamaStackDistribution instance requires a PostgreSQL database" is incorrect — introducing PostgreSQL is new work, not an extension of existing infrastructure.

**Correction 2 — A Red Hat PostgreSQL image with pgvector already exists.** The `registry.redhat.io/rhel9/postgresql-16` image includes pgvector out of the box — confirmed in the [sclorg/postgresql-container Dockerfile](https://github.com/sclorg/postgresql-container/blob/master/16/Dockerfile.rhel9) (`INSTALL_PKGS="$INSTALL_PKGS pgvector"`). PostgreSQL 18 (RHEL 9) also includes pgvector. Furthermore, the model-registry-operator already uses `postgresql-16` as its auto-provisioned database image, and `RELATED_IMAGE_POSTGRESQL_16_IMAGE` is already present in the rhods-operator CSV for disconnected installs. No custom image build is needed. No Konflux onboarding is needed. The 1-2 sprint image onboarding estimate in the strategy can be eliminated.

**Architectural direction — platform-level database vs. self-provisioned.** Multiple RHOAI components now need PostgreSQL (model-registry, MLflow, and now OGX for pgvector). The preferred long-term direction is a platform-provided shared PostgreSQL managed via the DSC, where each component consumes a connection string rather than self-provisioning. A shared platform-provided PostgreSQL via DSC will not be available until RHOAI 3.6. For 3.5, Gen AI Studio must provision its own PostgreSQL instance.

**Operator dependency for self-provisioning (RHAISTRAT-7164).** Self-provisioning PostgreSQL following the model-registry-operator pattern requires a RHOAI-controlled operator for Gen AI Studio. The ogx-k8s-operator is upstream and cannot carry RHOAI-specific provisioning logic. The dashboard operator modularization (RHAISTRAT-7164, In Progress) would provide this operator layer. This is a hard dependency — until RHAISTRAT-7164 delivers, there is no RHOAI-controlled operator where PostgreSQL lifecycle management can live. It will be challenging to commit this strategy to a specific release until that dependency is delivered.

**Fallback if RHAISTRAT-7164 does not land in time.** If the dashboard modularization is not ready for 3.5, the fallback is to require customers to bring their own PostgreSQL for RAG capabilities in the Playground. Users would manually configure the OGXServer CR spec with their PostgreSQL connection details. This aligns with the breaking changes introduced in OGX 1.0, even though the Playground largely abstracts OGX from users. The development team should define a go/no-go gate for this decision as part of sprint planning.

**Decouple from Auto Rag.** Auto Rag integration with Gen AI Studio (RHAISTRAT-7824) is targeting RHOAI 3.6. This strategy should validate pgvector only for Gen AI Studio Playground RAG workflows. Auto Rag compatibility with pgvector will be addressed in RHAISTRAT-7824's scope. Remove Auto Rag from affected components, impacted teams, acceptance criteria, and validation requirements.

**Performance and index thresholds — dev experimentation scope.** The default pgvector instance is meant for development experimentation, not production usage. Strict latency SLAs (p50/p95/p99) are not required. The sprint 1 benchmark should capture the inline Milvus baseline and verify pgvector is in the same order of magnitude, not meet a specific threshold. Typical Playground RAG usage involves small document sets — flat scan (no index) is sufficient for the default. Users with production-scale vector workloads should use an external vector database. Remove open questions about latency thresholds, corpus size ranges, and index type selection.

**PostgreSQL resource sizing.** Reference the model-registry-operator's PostgreSQL resource requests/limits as the starting point. Adjust based on sprint 1 benchmarking if needed.

**Alternative fallback — BFF-managed PostgreSQL provisioning.** If RHAISTRAT-7164 does not land in time, an alternative to requiring customers to bring their own PostgreSQL is to have the gen-ai BFF provision the PostgreSQL/pgvector instance directly, similar to how the BFF currently provisions guardrails infrastructure. The BFF would create the PostgreSQL Deployment, Service, PVC, and Secret when a playground with RAG is configured, if one does not already exist in the namespace. Caveats: (1) the implementation must be designed for portability — when the platform-provided shared database becomes available (3.6), the BFF should consume the shared connection string rather than self-provisioning; (2) lifecycle management of the PostgreSQL instance must be carefully considered — the BFF is not an operator with a reconciliation loop, so cleanup on playground deletion, handling of pod restarts, and credential rotation need explicit design attention.

**Existing remote vector store implementation is reusable.** Per the engineering team, the existing remote vector store implementation can be largely reused for pgvector integration. The majority of the work effort is around infrastructure and provisioning of the PostgreSQL/pgvector database, not the vector_io provider integration itself.

**Correction 3 — Vector storage and application storage are independent configurations.** The OGX vector_io provider configuration (`remote::pgvector` via `ENABLE_PGVECTOR`) is completely separate from OGX's application storage backend configuration (`storage.kv.type`, `storage.sql.type`). This strategy only needs to configure the pgvector vector_io provider — it does not change the application storage backend, which remains on its existing default (SQLite). There is no SQLite-to-PostgreSQL migration concern because the application storage is not being touched. Remove any references to consolidating vector and application storage in a single database, and remove any SQLite-to-PostgreSQL upgrade path considerations.
